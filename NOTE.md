# Что выбрали и почему
- Справочники dim_* описывают сущности (кто, что, где, когда), факты fact_* хранят события (заказ, позиция, платёж, отзыв).Факты разных уровней (заказ, позиция, платёж, отзыв) не дают смешать уровни: средний чек считается по заказу, выручка продавца по позиции. Новый сервис (доставка, возвраты) добавляется новым фактом без переделки старых.
- Покупатель определяется по customer_unique_id. customer_id выдаётся заново на каждый заказ (99 441 значение), а постоянный идентификатор человека даёт 96 096. customer_id остаётся в заказе как source_customer_id для сверки. Адрес доставки хранится в заказе, в справочнике только последний известный.
- Ничего не выбрасываем, проблемы помечаем флагами. Число строк в фактах равно raw. Заказы без позиций (775), без платежей (1), с противоречием статуса и дат (14) и с передачей в доставку раньше покупки (166) остаются в модели с флагами has_items, has_payment, dq_*. Отфильтровать их можно в запросе, вернуть выброшенное нельзя.
- Статусы, способы оплаты и категории вынесены в справочники. Что считать выручкой, задаётся флагами статуса, а не фильтром при загрузке. Готовой колонки «выручка» в фактах нет: цена и доставка хранятся раздельно, определение выручки живёт в mart. У 610 товаров нет категории, они получают служебную категорию 0; две категории без перевода сохранены (всего 74).
- Ключ отзывов составной. review_id не уникален (98 410 значений на 99 224 строки), у 547 заказов больше одного отзыва. Ключ (review_id, order_id), все отзывы сохранены.
- Платежи отдельным фактом. Сумма платежей не равна price + freight_value у 309 заказов (порог: разница больше 1; вероятные причины — ваучеры и проценты по рассрочке, не проверено). Поэтому выручку по платежам не считаем.
